# PlatformIO Example Standard

**Developed by Amine Saoud ibn al-Bashir.**

This document turns the master project specification into a practical checklist for every NanoKit-ESP32 example.

Official examples must compile with PlatformIO using the ESP32 Arduino framework and normal ESP32 GPIO numbers.

## Required Directory Layout

Every example should use this structure:

```text
example_name/
├── README.md                     # Goal, learning points, hardware, generated pin table, build, output
├── nanokit.yaml                  # Hardware manifest: the single source of truth for pins and components
├── platformio.ini
├── src/
│   └── main.cpp                  # Pin constants named in nanokit.yaml `symbol:` fields
├── include/
│   └── README.md
├── lib/
│   └── README.md
├── test/
│   └── README.md
├── assets/
│   └── README.md
├── images/
│   ├── connection-diagram.md     # GENERATED by tools/genius/generate.py
│   └── system-diagram.md         # GENERATED by tools/genius/generate.py
├── docs/
│   ├── Wiring.md                 # Generated connection table + hand-written wiring order and notes
│   └── Implementation_Guide.md   # Algorithm, flowchart, pseudocode, components, testing,
│                                 # troubleshooting, learning notes, exercises (hand-written)
└── .genius/
    ├── README.md                 # GENERATED status page
    ├── VALIDATION_REPORT.md      # GENERATED: rules checked, findings, code evidence
    └── project.json              # GENERATED: machine-readable copy
```

`examples_on_platformio/ultrasonic_distance/` is the reference layout. `Implementation_Guide.md` holds the algorithm, flowchart, pseudocode, components, testing, troubleshooting, learning notes, and exercises as sections; splitting them into separate files is optional for long examples.

Folders should not be left empty. If a folder has no source code yet, include a README explaining what belongs there and why the folder exists.

## Hardware Manifest and Generated Files

Every example that touches a board pin ships a `nanokit.yaml` (schema in `tools/genius/README.md`). Running `python tools/genius/generate.py`:

- validates every pin against `registry/nanokit-esp32.yaml` (flash pins, input-only pins, strapping pins, UART0, ADC2 with Wi-Fi, 5 V inputs, double assignment);
- cross-checks the `symbol:` constants in `src/` so documentation cannot drift from code;
- regenerates `images/connection-diagram.md`, `images/system-diagram.md`, the pin table between the `GENIUS:PIN_MAP` markers in `README.md`, the table between the `GENIUS:CONNECTION_TABLE` markers in `docs/Wiring.md`, and the `.genius/` reports.

Edit the manifest, never the generated blocks. The pre-commit hook and the GitHub workflow run the generator automatically.

## Required `platformio.ini`

Use this baseline unless the example needs extra libraries or build flags:

```ini
[env:nanokit_esp32]
; espressif32 8.0.0 = Arduino-ESP32 core 3.3.12, pinned so a platform update cannot break the build
platform = espressif32 @ 8.0.0
board = esp32dev
framework = arduino
monitor_speed = 115200
upload_speed = 921600
```

When libraries are needed, list them under `lib_deps` with a short explanation in the example README.

## Arduino-ESP32 Core Version

Always pin the platform version. An unpinned `platform = espressif32` silently follows PlatformIO's latest release, and the move from 7.x (Arduino-ESP32 core 2.0.17) to 8.0.0 (core 3.3.12) broke every example that used the 2.x LEDC and timer functions. The [PlatformIO Build workflow](../../.github/workflows/platformio-build.yml) compiles every project on each push, so a red check means a project no longer builds for a new user.

Write new code against the core 3.x API:

| Task | Core 3.x (use this) | Core 2.x (does not compile on 8.0.0) |
|---|---|---|
| Attach PWM to a pin | `ledcAttach(pin, freq, bits)` | `ledcSetup(channel, freq, bits)` + `ledcAttachPin(pin, channel)` |
| Attach PWM to a fixed channel | `ledcAttachChannel(pin, freq, bits, channel)` | same pair as above |
| Write a PWM duty | `ledcWrite(pin, duty)` or `ledcWriteChannel(channel, duty)` | `ledcWrite(channel, duty)` |
| Start a hardware timer | `timerBegin(1000000)` (tick rate in Hz) | `timerBegin(0, 80, true)` |
| Attach a timer ISR | `timerAttachInterrupt(timer, isr)` | `timerAttachInterrupt(timer, isr, true)` |
| Periodic alarm | `timerAlarm(timer, ticks, true, 0)` | `timerAlarmWrite(timer, ticks, true)` + `timerAlarmEnable(timer)` |
| Built-in Hall sensor | not available | `hallRead()` |

The only exception is `examples_on_platformio/hall_sensor/`, which pins `platform = espressif32 @ 6.13.0` (core 2.0.17) because the built-in Hall sensor was removed in core 3.x.

## Hardware Documentation Rules

Every GPIO used in an example must be documented using this table:

| NanoKit Pin | GPIO | Component Pin | Direction | Reason | Electrical Notes |
|---:|---|---|---|---|---|
| 17 | GPIO2 | Onboard LED | Output | Safe first digital output and PWM-capable pin | 3.3 V logic |

Use `docs/hardware/nanokit-integrated-esp32-pinout.md` as the source of truth.

## Wiring Document

Every hardware example that uses board pins must include `docs/Wiring.md`.

The wiring table must use this mapping:

```text
NanoKit Pin -> GPIO -> Electronic Component Pin -> Description
```

Example:

| NanoKit Pin | GPIO | Component Pin | Description |
|---:|---|---|---|
| 23 | GPIO21 | OLED SDA | I2C data line |
| 18 | GPIO22 | OLED SCL | I2C clock line |
| 12 or 31 | GND | OLED GND | Common ground |
| 13 or 14 | 3V3 | OLED VCC | 3.3 V power |

## Code Requirements

Source code should be educational and maintainable.

- Use meaningful constants for GPIO pins.
- Explain why each GPIO was selected.
- Avoid magic numbers in logic.
- Keep `setup()` and `loop()` readable.
- Extract helper functions when it improves clarity.
- Comment important lines with intent, not just syntax.
- Avoid unsafe pins listed in the hardware reference.

Example:

```cpp
const int LED_PIN = 2;  // NanoKit Pin 17, GPIO2, onboard LED and PWM-capable safe output.

void setup() {
  pinMode(LED_PIN, OUTPUT);  // Configure GPIO2 as an output so the ESP32 can drive the onboard LED.
}
```

## Required Documentation Files

| File | Purpose | Source |
|---|---|---|
| `nanokit.yaml` | Components, buses, pins, power, status. | hand-written |
| `docs/Wiring.md` | Generated connection table plus wiring order and electrical notes. | mixed |
| `docs/Implementation_Guide.md` | Algorithm, Mermaid flowchart, pseudocode, components, testing, troubleshooting, learning notes, exercises. | hand-written |
| `images/connection-diagram.md` | Physical wiring with `Pin <NanoKit pin> / GPIO<n>` labels. | generated |
| `images/system-diagram.md` | Every component grouped by node and bus with Confirmed / Proposed / Blocked styling. | generated |
| `.genius/VALIDATION_REPORT.md` | Rules checked, findings, and code evidence. | generated |

Long examples may split `Implementation_Guide.md` into `Algorithm.md`, `Flowchart.md`, `Pseudocode.md`, `Components.md`, `Testing.md`, `Troubleshooting.md`, `Learning_Notes.md`, and `Exercises.md`; the content requirements are the same.

## Diagram Policy

Prefer diagrams that are useful for learning:

- Connection diagram
- Breadboard diagram
- Block diagram
- System architecture diagram
- Flowchart

If a generated image is not available yet, include a Mermaid diagram or a clear Markdown diagram source that can be rendered later.

## Definition of Done

An example is complete only when:

- `platformio.ini` exists.
- `src/main.cpp` exists.
- `nanokit.yaml` exists and `python tools/genius/generate.py --check` reports no error.
- Source code is educational and maintainable.
- GPIO choices are explained.
- Pin mapping is documented.
- Wiring is documented when hardware is used.
- Algorithm, flowchart, and pseudocode are present when useful.
- Components and testing notes exist.
- Troubleshooting notes exist.
- Exercises or suggested improvements exist.
- The example can be built with PlatformIO.

## Build Command

From the example directory:

```bash
pio run
```

If PlatformIO is not installed, install it through the official PlatformIO extension or CLI before building.
