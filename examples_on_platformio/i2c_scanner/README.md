# I2C Scanner

**Developed by Amine Saoud ibn al-Bashir.**

The first thing to do with any new I2C module is to find out whether NanoKit can see it, and at which address. This example turns NanoKit Integrated ESP32 into a bus scanner: it probes every legal 7-bit address on the I2C0 bus, prints the ones that answer, and tells you what to check when nothing does.

## Goal

Scan addresses 0x08 to 0x77 on the NanoKit I2C0 bus every 5 s, print each responding address in hexadecimal with a hint of the usual chip, count the devices, and give a clear three-point checklist when the bus is empty.

## What You Will Learn

- How `Wire.begin(sda, scl)` routes the ESP32 I2C peripheral to the NanoKit I2C0 pins (Pin 23 / GPIO21 and Pin 18 / GPIO22).
- What a 7-bit I2C address is, and why the first and last few addresses are never used by a device.
- How `Wire.beginTransmission` / `Wire.endTransmission` detect a device through the acknowledge (ACK) bit.
- Why I2C lines are open-drain and therefore need pull-up resistors to 3.3 V.
- Why 100 kHz is the right clock for scanning, even if the device supports faster modes.

## Hardware Required

| Item | Quantity | Notes |
|---|---:|---|
| NanoKit Integrated ESP32 | 1 | Main controller board |
| Any 3.3 V I2C module | 1 or more | OLED (SSD1306), BME280, MPU-6050, DS3231, ... |
| Jumper wires | 4 | VCC, GND, SDA, SCL |
| 4.7 kOhm resistor | 2 | Optional: only if the module has no pull-ups of its own |
| Breadboard | 1 | Optional but recommended |

## How It Works

1. `Wire.begin(I2C_SDA_PIN, I2C_SCL_PIN)` connects the I2C0 peripheral to GPIO21 (SDA) and GPIO22 (SCL), and `Wire.setClock(100000)` selects the 100 kHz standard mode.
2. Every 5 s the firmware loops over addresses 0x08 to 0x77. For each one it calls `Wire.beginTransmission(address)` and `Wire.endTransmission()`, which sends a START condition and the address byte and then waits for the ninth clock pulse.
3. A device that recognises its address pulls SDA low during that ninth pulse (ACK), so `endTransmission()` returns 0. If nobody answers, SDA stays high (NACK) and the function returns 2.
4. Every acknowledged address is printed in hexadecimal together with a hint from a small built-in table of common chips.
5. If no address answered, the firmware prints the three usual causes: no power, SDA and SCL swapped, or missing pull-ups. If addresses timed out instead of answering NACK, it also reports that a line is probably held low.

## Build and Upload

```bash
pio run
pio run --target upload
pio device monitor -b 115200
```

## Expected Output

With an OLED display plugged in, then a BME280 added during the run:

```text
NanoKit I2C scanner ready.
Bus: SDA on NanoKit Pin 23 / GPIO21, SCL on NanoKit Pin 18 / GPIO22, 100 kHz.
Scanning addresses 0x08-0x77 every 5 s. Plug a module in at any time.
Scan 1:
  Found device at 0x3C  -> SSD1306 OLED display
  1 device found.
Scan 2:
  Found device at 0x3C  -> SSD1306 OLED display
  Found device at 0x76  -> BME280 / BMP280 environment sensor
  2 devices found.
```

With nothing connected:

```text
Scan 1:
  No device answered. Check, in this order:
  1. Power: module VCC on 3V3 (NanoKit Pin 13 or 14), GND on NanoKit Pin 12 or 31.
  2. Wires: SDA on NanoKit Pin 23 / GPIO21 and SCL on NanoKit Pin 18 / GPIO22, not swapped.
  3. Pull-ups: both lines need a resistor to 3.3 V; add 4.7 kOhm if the module has none.
```

## Safety Notes

Power the module from 3V3 (NanoKit Pin 13 or 14) only. A module that needs 5 V usually pulls its SDA and SCL lines up to 5 V as well, and 5 V on a NanoKit GPIO exceeds the 3.3 V rating; use a bidirectional level shifter for such modules. Never connect SDA or SCL to the 5 V rail (NanoKit Pin 11 or 32), and double-check that VCC and GND are not reversed before powering a module: reversed power is the most common way to destroy a breakout board.
