# Dual Core Tasks

**Developed by Amine Saoud ibn al-Bashir.**

The ESP32 inside NanoKit Integrated ESP32 has two processor cores, and the Arduino `loop()` only ever uses one of them. This example creates two FreeRTOS tasks, pins one to each core, and lets each blink its own LED at its own rhythm while `loop()` keeps an eye on memory.

## Goal

Run `blinkCore0Task` on core 0 (external LED, 1000 ms) and `blinkCore1Task` on core 1 (onboard LED, 300 ms) at the same time, prove on which core each one runs, and print free heap and the stack high-water mark of both tasks every 5 s from `loop()`.

## What You Will Learn

- How `xTaskCreatePinnedToCore` creates a task and ties it to core 0 or core 1.
- That `setup()` and `loop()` are themselves a FreeRTOS task running on core 1 by default.
- Why a task waits with `vTaskDelay(pdMS_TO_TICKS(...))` and never with `delay()`.
- What `uxTaskGetStackHighWaterMark` and `ESP.getFreeHeap()` tell you about memory, and how to size a task stack.
- Why core 0 is shared with the Wi-Fi and Bluetooth stacks, and what that means for time-critical code.
- Why two cores printing to one `Serial` port can interleave their text.

## Hardware Required

| Item | Quantity | Notes |
|---|---:|---|
| NanoKit Integrated ESP32 | 1 | Main controller board |
| LED (any colour) | 1 | Blinked by the core 0 task |
| 220 ohm resistor | 1 | Current limit for the LED |
| Jumper wires | 2 | LED anode via resistor, LED cathode |
| Breadboard | 1 | Optional but recommended |

The onboard LED on NanoKit Pin 17 / GPIO2 is blinked by the core 1 task, so the example already shows something with no wiring at all.

## How It Works

1. `setup()` configures GPIO26 and GPIO2 as outputs and prints the core it runs on (core 1, where the Arduino core places the loop task).
2. `xTaskCreatePinnedToCore` is called twice: `blinkCore0Task` with core id 0 and `blinkCore1Task` with core id 1, each with a 2048-byte stack and priority 1. The scheduler starts them immediately.
3. Each task prints its name together with `xPortGetCoreID()` once, which reads the id of the core that is executing the line, then enters an endless loop: toggle its LED, sleep with `vTaskDelay(pdMS_TO_TICKS(period))`.
4. While a task sleeps, its core is free for other tasks: the idle task, the Wi-Fi stack on core 0, or `loop()` on core 1.
5. Every 5 s `loop()` prints `ESP.getFreeHeap()` and `uxTaskGetStackHighWaterMark()` for both task handles. The high-water mark is the smallest amount of stack that has ever been free, so it tells you how close each task is to overflowing.

```bash
pio run

```

## Expected Output

```text
NanoKit dual core tasks example ready.
setup() and loop() run on core 1
LEDs: core 0 task on NanoKit Pin 37 / GPIO26 (1000 ms), core 1 task on NanoKit Pin 17 / GPIO2 (300 ms).
blinkCore0Task started on core 0
blinkCore1Task started on core 1
Report | free heap: 294000 B | stack never used: core0 task 1500 B, core1 task 1500 B
Report | free heap: 294000 B | stack never used: core0 task 1500 B, core1 task 1500 B
```

The exact numbers depend on the core version; what matters is that they stay constant from one report to the next. The two task start lines may occasionally appear mixed together, because both cores write to the same `Serial` port at the same moment.

## Safety Notes

Never connect an LED directly between a GPIO and GND without a resistor; the GPIO can be damaged by the current. Keep the LED cathode on GND (NanoKit Pin 12 or 31) and never on the 5 V rail (NanoKit Pin 11 or 32): NanoKit GPIOs are 3.3 V only. On the software side, a task that never calls `vTaskDelay` (or another blocking call) on core 0 starves the idle task there and triggers the task watchdog, which resets the board; always give a task a place to sleep.
