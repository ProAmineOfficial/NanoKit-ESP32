# Preferences Flash Storage

**Developed by Amine Saoud ibn al-Bashir.**

Variables in RAM vanish at every reset. This example shows how NanoKit Integrated ESP32 remembers things across resets and power loss with the `Preferences` library, which stores key/value pairs in the Non-Volatile Storage (NVS) area of the flash chip. A boot counter and the state of the onboard LED are kept there; a push button changes the LED and saves it.

## Goal

Count how many times the board has booted, restore the LED to the state it had before the last reset, toggle and save that state on every debounced button press, and offer two Serial commands: `stats` to print the stored values and `clear` to erase them and reboot.

## What You Will Learn

- How `Preferences` opens a named area of NVS flash (`prefs.begin("nanokit", false)`) and reads or writes typed keys (`getUInt`, `putUInt`, `getBool`, `putBool`).
- What a namespace and a key are, and why both names are limited to 15 characters.
- The difference between opening a namespace read-only and read-write.
- Why flash must be written only when something actually changed (here: on a button press), never in every loop pass.
- How to read a Serial command line by line without blocking the loop.
- Why `Preferences` is preferred over the old `EEPROM` emulation on the ESP32.

## Hardware Required

| Item | Quantity | Notes |
|---|---:|---|
| NanoKit Integrated ESP32 | 1 | Main controller board |
| Push button (momentary, normally open) | 1 | Any tactile switch |
| Jumper wires | 2 | Button to GPIO4 and to GND |
| Breadboard | 1 | Optional but recommended |

The LED is the onboard one on NanoKit Pin 17 / GPIO2, so no extra LED or resistor is needed.

## How It Works

1. `setup()` opens the `nanokit` namespace in read-write mode. On a fresh chip the namespace does not exist yet and is created.
2. It reads the `boots` key (default 0 when the key is absent), adds 1, writes it back, and prints it. This is the only flash write that is not caused by a button press.
3. It reads the `led` key (default `false`) and drives GPIO2 accordingly, so the LED comes back exactly as it was before the reset.
4. `loop()` debounces GPIO4 with the same `millis()` window as the Digital Input Output example. On each press edge it toggles the LED and calls `prefs.putBool("led", ...)` once.
5. `loop()` also collects characters from `Serial` until a newline. `stats` prints the boot count, the LED state, and `prefs.freeEntries()`; `clear` erases the whole namespace, closes it, and calls `ESP.restart()`, after which the counter starts again at 1.

## Build and Upload

```bash
pio run
pio run --target upload
pio device monitor -b 115200
```

To type commands, press Enter after `stats` or `clear`. Add `--echo` to the monitor command if you want to see what you type.

## Expected Output

First boot after flashing, two presses, then a reset with the EN button:

```text
NanoKit Preferences flash storage example ready.
Button: NanoKit Pin 10 / GPIO4 (to GND). LED: onboard, NanoKit Pin 17 / GPIO2.
Press the button to toggle and save the LED. Serial commands: stats, clear.
Stats | boots: 1 | LED: OFF | free NVS entries: 628
Saved | LED: ON
Saved | LED: OFF
Saved | LED: ON
NanoKit Preferences flash storage example ready.
Button: NanoKit Pin 10 / GPIO4 (to GND). LED: onboard, NanoKit Pin 17 / GPIO2.
Press the button to toggle and save the LED. Serial commands: stats, clear.
Stats | boots: 2 | LED: ON | free NVS entries: 628
```

The LED is lit immediately after the second start, before anyone touches the button. Typing `clear` prints `Namespace cleared. Rebooting; the boot counter restarts at 1.` and the board restarts with `boots: 1` and the LED off. The free-entries figure depends on the partition table and on what other firmware has stored; what matters is that it does not keep shrinking.

## Safety Notes

The button only ever connects GPIO4 to GND, which is always safe; never wire it to 5 V (NanoKit Pin 11 or 32) because NanoKit GPIOs are 3.3 V only. On the software side, never put a `put...()` call where it runs on every loop pass: NVS flash tolerates a limited number of erase cycles per sector, and a loop that writes thousands of times per second can wear a sector out in days. Write when a value changes, as this example does.
